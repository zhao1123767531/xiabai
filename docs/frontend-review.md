# 前端审查

审查日期：2026-05-29

## 结论

当前实现已经覆盖了核心视觉风格、房间首页、大厅、发身份、查看释义、验证、揭晓和记分榜，是一个完整度较高的单机演示原型。但它还不是可上线的联机游戏：房间、玩家加入、踢人、同步状态、私密身份保护都还停留在前端模拟层。

## 已符合规则的部分

- 首页包含创建房间、加入房间和玩法说明。
- 创建房间会生成 4 位房间号。
- 大厅展示房主、玩家列表、人数上限 12，以及至少 4 人才能开始。
- 每轮分配 1 名老实人、1 名大聪明，其余为瞎掰人。
- 老实人身份在讨论和揭晓阶段公开展示。
- 生僻词与释义交互完整：老实人看到真释义，其他身份看到“不知道释义”的提示，弹窗 10 秒后关闭且每轮只能查看一次。
- 每道题展示 3 个候选方向，老实人在释义弹窗中可见正确方向，揭晓阶段全员可见正确方向。
- 老实人可以在讨论阶段发起换题，二次确认后更换本轮词语并重置释义查看状态。
- 验证后会公布全员身份，并支持下一轮。
- 记分规则与描述一致：押中老实人双方得分，押中瞎掰人则被押中的瞎掰人得分。
- 主题色清晰：大聪明橙色、老实人蓝色、瞎掰人红色。

## 主要风险

1. 私密身份只在 UI 层隐藏，没有真正服务端隔离。

   原型中所有玩家身份都存在同一个前端状态对象里。只要打开调试工具，或使用演示视角切换，就能看到所有身份。正式版必须由后端按玩家连接单独下发自己的身份，只公开老实人身份。

2. 房间是本地模拟，不是真联机。

   创建房间、加入房间、玩家加入、请出玩家都没有后端状态。不同设备输入同一个房间号不会进入同一个真实房间。

3. 房主权限需要后端校验。

   当前 `isHost` 只是前端字段，任何人都可以篡改。正式版里开始游戏、请出玩家、下一轮必须由后端验证房主身份。

4. 管理后台鉴权不能放在前端。

   词库管理入口只能用于本地演示。正式版词库管理需要登录态、服务端鉴权和审计。

5. 规则文案存在一个需要确认的歧义。

   需求第 5 点写“由瞎掰人点击一个人的头像，点击验证”，但记分规则写“大聪明选中老实人/瞎掰人”。当前实现按记分规则处理，由大聪明完成验证。建议产品规则统一为“大聪明验证”。

## 建议的前端改造

- 接入实时房间 API 后，把房间状态拆成 `publicRoomState` 和 `privatePlayerState`。
- 删除正式版本的玩家视角切换，仅在 `?demo=1` 下保留演示能力。
- 给加入房间增加昵称输入，避免所有真实玩家只能使用随机昵称。
- 房主操作使用服务端确认后的状态回放，不在前端直接假定成功。
- 验证阶段只给大聪明展示可点击头像和验证按钮，其他玩家只看到等待状态。
- 管理后台迁移到独立受保护页面，前端只保留词库展示或禁用入口。
- 建议增加空房间、房间不存在、房间已满、玩家掉线、房主离开、重连恢复等状态页。

## 当前前端小改动

- 新增干净入口 `index.html`，避免原压缩包中的乱码 HTML 文件名问题。
- 新增 `app/config.js`，将单设备视角切换标记为演示模式能力。
- 新增题目方向字段与老实人换题交互，默认题库扩展为更适合瞎掰的生僻词/成语组合。
- 新增 `README.md`、本审查文档和后端设计文档，便于后续进入真实开发。
